## 2. What 0.1 does

A person describes a system in a few small YAML files: its parts ("boxes"), in three levels, and the connections between them ("edges"). Vockpit checks the files, generates one diagram per level, and shows them in a web page where clicking a box zooms into it.

| In scope | Out of scope (later releases) |
|---|---|
| Registry of boxes, actors and edges | Tables, screens, flows, technology components, layers |
| Commands `init`, `generate`, `check`, `view` | Links to code or tests, status colours, fault location |
| Checks C01, C02, C03, C10, C26 | Specs, changes, vetting, approval |
| Generated D2 diagrams and SVGs | EGM, hooks, rules, project template |
| Static viewer page with click-to-zoom | Editing the model from the viewer |
| One agent skill, `pack-draft` | Any other skill |
| One example system, and Vockpit's own model | A server, a database, user accounts |

## 5. The registry

A **project** is any folder containing `model/system.yaml`. All commands act on the project in the current folder, or the one given with `--root <path>`.

### 5.1 Kinds of item

| Kind | Declared in | Meaning |
|---|---|---|
| **system** | `model/system.yaml`, key `system` | The whole system. Exactly one. |
| **actor** | `model/system.yaml`, key `actors` | A person or outside system that the system talks to |
| **L1 box** | `model/system.yaml`, key `boxes` | A subsystem. Its parent is the system. |
| **L2 box** | `model/boxes/<l1-id>.yaml`, key `boxes` | A component inside one L1 box |
| **edge** | key `edges` in any model file | A directed connection carrying named data |

There are exactly three levels: L0 is the system, L1 its subsystems, L2 their components. An L2 box cannot have children.

### 5.2 `model/system.yaml`

```yaml
system:
  id: shop                      # required
  title: Online Shop            # required
  summary: Sells goods online.  # required
actors:                         # optional list
  - id: customer                # required
    title: Customer             # required
    kind: person                # required: person | external
    summary: Buys goods.        # optional
boxes:                          # required, at least one
  - id: orders                  # required
    title: Orders               # required
    summary: Takes and tracks orders.   # required
    inputs:  [Cart]             # optional list of strings
    outputs: [Order]            # optional list of strings
edges:                          # optional list
  - from: customer              # required: id of an actor or a box
    to: storefront              # required: id of an actor or a box
    data: Browse and buy        # required, non-empty string
```

### 5.3 `model/boxes/<l1-id>.yaml`

```yaml
parent: orders                  # required; must equal the file name without .yaml
boxes:                          # required, at least one; same fields as an L1 box
  - id: create-order
    title: Create order
    summary: Validates a cart and stores the order.
edges:                          # optional; same fields as above
  - { from: order-controller, to: create-order, data: OrderRequest }
```

An L1 box with no file under `model/boxes/` simply has no children. That is allowed.

### 5.4 Rules for IDs

- An ID matches `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` (lowercase letters, digits, single hyphens).
- IDs are unique across the whole project: system, actors and all boxes share one namespace.
- An edge may be declared in any model file and may connect items from different files.

### 5.5 The loaded model

`registry.load(root)` returns a `Model` and a list of findings. The `Model` holds, in declaration order (the system file first, then box files sorted by file name):

- `system`: id, title, summary
- `actors`: list
- `boxes`: list; each has id, title, summary, inputs, outputs, `parent` (an id), `level` (1 or 2), `children` (list of ids), `source` (the file it came from, as a path relative to the project root with forward slashes)
- `edges`: list of from, to, data, source

`level` and `children` are computed. They are never written in YAML.

## 6. Findings and checks

### 6.1 Finding format

A finding has: `rule` (for example `C02`), `severity` (`ERROR` or `WARN`), `location` (a file path relative to the project root, forward slashes), `message`.

Printed as one line:

```text
C02 ERROR model/boxes/orders.yaml: duplicate id 'create-order' (also in model/system.yaml)
```

Findings are printed sorted by rule, then location, then message.

### 6.2 Rules

| Rule | Severity | Fails when |
|---|---|---|
| **C01** Schema | ERROR | `model/system.yaml` is missing; a file is not valid YAML; a required key is missing; a value has the wrong type; a key is present that this specification does not define; an ID does not match the pattern; `kind` is not `person` or `external`; a list that must have at least one entry is empty; a `boxes/*.yaml` file's `parent` differs from its file name |
| **C02** Identity | ERROR | Two items share an ID; a `boxes/*.yaml` file's `parent` is not the ID of an L1 box |
| **C03** Edges | ERROR | An edge's `from` or `to` is not the ID of an actor or a box (the system ID is not allowed); `from` equals `to`; both ends are actors |
| **C10** Freshness | ERROR | The set of `.d2` files in `docs/diagrams/` differs from the set a fresh generation would produce; the text of any `.d2` file differs; `docs/viewer/model.js` is missing or differs. Compare after converting CRLF to LF. |
| **C10** Freshness | WARN | A `.d2` file has no `.svg` beside it, or `docs/viewer/diagrams.js` is missing |
| **C26** Size | WARN | A diagram has more than 12 nodes, counting neighbour nodes. Message names the diagram and the count. |

### 6.3 Order

1. Run C01. If it produces any ERROR, print the findings and stop. The other rules need a loadable model.
2. Run C02 and C03. If either produces an ERROR, print and stop.
3. Run C10 and C26.

## 7. Diagrams

`diagrams.build(model)` returns a list of `Diagram` objects. A `Diagram` has a `name`, a `title`, a list of nodes and a list of edges. It knows nothing about D2.

### 7.1 Which diagrams exist

| Name | Exists when | Shows |
|---|---|---|
| `L0_context` | Always | The system as one node, and every actor |
| `L1_system` | Always | The L1 boxes |
| `L2_<id>` | For each L1 box that has children | That box's L2 boxes |

### 7.2 Diagram nodes

Each node has: `id`, `title`, `summary`, `role` and `link`.

| Role | Meaning | Drawn as |
|---|---|---|
| `system` | The system, in `L0_context` only | Rectangle, bold border |
| `inner` | A box that belongs to this diagram | Rectangle |
| `person` | An actor of kind `person` | D2 `shape: person` |
| `external` | An actor of kind `external` | Rectangle, dashed border |
| `neighbour` | A box outside this diagram that an inner box connects to | Rectangle, dashed border, grey fill |

`link` is `#/<id>` for roles `system`, `inner` and `neighbour`. Actors have no link.

### 7.3 `L0_context`

- Nodes: the system (role `system`), then every actor in declaration order.
- Edges: for every registry edge with one end an actor and the other end a box, draw an edge between the actor and the system, keeping the direction. Ignore edges between two boxes.

### 7.4 `L1_system` and `L2_<id>`

Let **F** be the focus: the system for `L1_system`, or the L1 box for `L2_<id>`.

- **Inner nodes**: the children of F, in declaration order.
- For each end `x` of each registry edge, find its **representative**:
  - `x` is an actor: `x` itself, with its actor role.
  - `x` is a child of F: `x` itself (inner).
  - `x` is a grandchild of F (only possible when F is the system): the L1 parent of `x` (inner).
  - Otherwise `x` is a box outside F: the L1 box that is `x` or contains `x`, with role `neighbour`.
- **Keep** an edge only if at least one representative is an inner node and the two representatives differ.
- **Neighbour and actor nodes**: every non-inner representative of a kept edge, sorted by ID, listed after the inner nodes.

### 7.5 Merging edges (all diagrams)

After mapping, edges with the same (from, to) pair become one edge. Its label is the distinct `data` values, sorted alphabetically, joined with `; `. Edges are listed sorted by from, then to. Two edges in opposite directions stay separate.

## 8. D2 output

`d2.render(diagram)` returns the text of one `.d2` file. The output must be identical for identical input.

### 8.1 Format

```d2
# GENERATED by vockpit 0.1.0 from model/. Do not edit.
direction: right

title: |md # L2: Orders | { near: top-center }

classes: {
  system:    { style: { stroke-width: 3; border-radius: 6 } }
  inner:     { style: { border-radius: 6 } }
  external:  { style: { stroke-dash: 4; border-radius: 6 } }
  neighbour: { style: { stroke-dash: 4; border-radius: 6; fill: "#eeeeee" } }
}

n_create_order: "Create order" {
  class: inner
  link: "#/create-order"
  tooltip: "Validates a cart and stores the order."
}
n_customer: "Customer" {
  shape: person
}

n_order_controller -> n_create_order: "OrderRequest"
```

### 8.2 Rules

- The D2 key of a node is `n_` followed by the ID with every `-` replaced by `_`. This avoids clashes with D2 keywords.
- Titles, tooltips and labels are double-quoted. Escape `\` as `\\` and `"` as `\"`. Replace newlines with a space.
- Diagram titles: `L0: <system title>`, `L1: <system title>`, `L2: <box title>`.
- Nodes are written in the order given by the diagram, then edges.
- Files are written to `docs/diagrams/<name>.d2`.

### 8.3 Rendering to SVG

`d2.to_svg(d2_path, svg_path)` runs `d2 <d2_path> <svg_path>`. Find the tool with `shutil.which("d2")`. If it is not found, `generate` exits with code 2 and prints: `d2 not found on PATH. Install from https://d2lang.com or use --no-svg.`

### 8.4 Check this before building further

D2 must keep `link: "#/create-order"` as an `href` of `#/create-order` in the SVG. This was confirmed on 2026-11-10 with D2 v0.9.0 on the development machine, using the sample in section 8.1. **Task 5 in section 14 tests it again**, since other D2 versions may differ. If D2 rejects or rewrites the value, use `link: "https://vockpit.invalid/#/create-order"` instead, and have the viewer treat any link starting with `https://vockpit.invalid/#/` as an in-page route. Tell the human which form was used.

## 9. Viewer data

`generate` writes two files into `docs/viewer/`.

### 9.1 `model.js`

```js
window.VOCKPIT_MODEL = {
  "version": 1,
  "generator": "vockpit 0.1.0",
  "system": "shop",
  "nodes": {
    "shop":   { "id": "shop", "kind": "system", "title": "...", "summary": "...", "level": 0, "parent": null, "children": ["storefront", "orders"], "inputs": [], "outputs": [], "diagram": "L1_system" },
    "orders": { "id": "orders", "kind": "box", "level": 1, "parent": "shop", "children": ["create-order"], "diagram": "L2_orders", "...": "..." },
    "create-order": { "id": "create-order", "kind": "box", "level": 2, "parent": "orders", "children": [], "diagram": "L2_orders", "...": "..." },
    "customer": { "id": "customer", "kind": "person", "level": null, "parent": null, "children": [], "diagram": "L0_context", "...": "..." }
  },
  "edges": [ { "from": "customer", "to": "storefront", "data": "Browse and buy" } ],
  "diagrams": { "L0_context": { "title": "L0: Online Shop" }, "L1_system": { "title": "L1: Online Shop" } }
};
```

- `diagram` is the diagram to show when the node is the focus: for the system, `L1_system`; for an L1 box with children, its `L2_<id>`; for any box without children, the diagram that contains it as an inner node; for an actor, `L0_context`.
- Every node has every field shown for `shop`.
- Written with `json.dumps(..., indent=2, sort_keys=True, ensure_ascii=False)`, preceded by `window.VOCKPIT_MODEL = ` and followed by `;` and a newline.

### 9.2 `diagrams.js`

```js
window.VOCKPIT_SVG = { "L0_context": "<svg ...>...</svg>", "L1_system": "..." };
```

Each value is the full text of the SVG file. With `--no-svg`, this file is written as `window.VOCKPIT_SVG = {};`.

### 9.3 `index.html`

`generate` copies `assets/viewer/index.html` to `docs/viewer/index.html`, overwriting it.

## 10. The viewer

One file, `index.html`. It loads `model.js` and `diagrams.js` with `<script src>` tags, so it works when opened straight from disk and when served by GitHub Pages.

### 10.1 Layout

```text
+--------------------------------------------------------------------------+
| Vockpit   You steer. AI builds.                                          |
| Context > Online Shop > Orders > Create order              [ Zoom out ]  |
+--------------------------------------------------+-----------------------+
|                                                  | Create order          |
|                                                  | create-order · L2     |
|            diagram (inline SVG)                  | Summary               |
|                                                  | Inputs / Outputs      |
|                                                  | Receives from / Sends |
|                                                  | to                    |
+--------------------------------------------------+-----------------------+
```

### 10.2 Routes

The route is the part of the page address after `#/`.

| Route | Diagram shown | Inspector shows |
|---|---|---|
| empty (`#/` or no hash) | `L0_context` | The system |
| the system's ID | `L1_system` | The system |
| an L1 box with children | its `L2_<id>` | That box |
| any box without children | The diagram named in its `diagram` field, with that node highlighted | That box |
| an unknown ID | `L0_context` | A message: `No item with id '<id>'.` |

The viewer redraws on every `hashchange` event. Because the links inside the SVG are `#/<id>`, clicking a node changes the route with no extra code.

### 10.3 Behaviour

1. **Zoom in**: click a node. Its link changes the route.
2. **Zoom out**: the button, or the Escape key, goes to the parent's route. From an L2 leaf to its L1 parent; from an L1 box to the system; from the system to the empty route. Disabled on the empty route.
3. **Breadcrumb**: always starts with `Context` (the empty route), then the system, then the path to the focus. Every part except the last is a link.
4. **Highlight**: when the focus is a box without children, add a CSS class to the SVG `<a>` element whose link ends in `#/<focus id>`, and style it with a thick coloured outline.
5. **Inspector**: title; ID and level; summary; inputs and outputs if any; "Receives from" and "Sends to", each a list of `<other item's title>: <data>` built from the edges that touch the focus directly, where each title is a link to that item's route; and, if the focus has children, the line `Contains N boxes`.
6. **Pan and zoom the picture**: mouse wheel scales the SVG around the pointer; dragging pans; double-click resets to fit. This changes only the picture's size and position, not the route.
7. **Missing picture**: if `VOCKPIT_SVG` has no entry for the diagram, show in the diagram area: `Diagram not rendered. Run "vockpit generate" with d2 installed.` The inspector and breadcrumb still work.
8. **Appearance**: follows the browser's light or dark setting through `prefers-color-scheme`. In dark mode the SVG sits on a light panel so D2's colours stay readable. Readable at 1280 pixels wide and on a phone, where the inspector moves below the diagram.
9. **No network**: the page makes no request other than for `model.js` and `diagrams.js`.

## 11. Commands

All commands accept `--root <path>` (default: current folder). Findings and messages go to standard output; usage errors go to standard error.

| Exit code | Meaning |
|---|---|
| 0 | Success. Warnings do not change this. |
| 1 | At least one ERROR finding |
| 2 | Wrong usage, no project found, or `d2` missing when needed |

### 11.1 `vockpit init [path]`

Creates a starter project in `path` (default: current folder; the folder is created if missing).

| Creates | From |
|---|---|
| `model/system.yaml` | `assets/init/system.yaml`: system `my-system`, actor `user` (person), L1 box `core`, one edge from `user` to `core` |
| `model/boxes/` | empty folder with a `.gitkeep` |
| `brief.md` | `assets/init/brief.md` (section 11.5) |
| `.claude/skills/pack-draft/SKILL.md` and `.agent/skills/pack-draft/SKILL.md` | `assets/init/pack-draft/SKILL.md` (section 11.6) |
| `docs/diagrams/`, `docs/viewer/` | by running `generate` at the end (with `--no-svg` and a printed notice if `d2` is not found) |

An existing file is never overwritten: print `skip <path> (exists)` and continue. If `model/system.yaml` already existed, do not run `generate`. Print one line per file created. After `init` in an empty folder, `vockpit check` must exit 0.

### 11.2 `vockpit generate [--no-svg]`

1. Load the model and run C01, C02 and C03. On any ERROR, print the findings, write nothing, exit 1.
2. Delete every `.d2` and `.svg` file in `docs/diagrams/`. Write the new `.d2` files.
3. Unless `--no-svg`: render each `.d2` to `.svg`.
4. Write `docs/viewer/model.js`, `diagrams.js` and `index.html`.
5. Print one line per diagram, then `Generated N diagrams.` Print any C26 warnings.

### 11.3 `vockpit check`

Runs the rules as in section 6.3. Prints findings, then a last line: `OK` if there are no findings; `OK with N warning(s)` if only warnings; `FAILED: N error(s), M warning(s)` otherwise. Exits 0 or 1.

### 11.4 `vockpit view [id]`

Requires `docs/viewer/index.html` to exist; if not, print `Run "vockpit generate" first.` and exit 2. If `id` is given and is not in the model, print `No item with id '<id>'.` and exit 2. Otherwise print the address of the page (a `file://` address ending in `#/<id>` when given) and open it with Python's `webbrowser` module. `--no-open` prints the address without opening it.

### 11.5 `brief.md` starter

```markdown
# Brief

Describe the system in plain words. An AI agent will turn this into the model.

## What is it for?

## Who uses it, and which outside systems does it talk to?

## What are its main parts?

## What passes between the parts?
```

### 11.6 The `pack-draft` skill

`SKILL.md`, in full:

```markdown
---
name: pack-draft
description: Turn brief.md into a Vockpit model (model/system.yaml and model/boxes/*.yaml) and generate the drill-down diagrams. Use when the user asks to draft, model or diagram a system from a brief.
---

# Draft the model from the brief

1. Read `brief.md`. If it is empty, ask the user to describe the system and stop.
2. Write `model/system.yaml`:
   - `system`: one id, title and one-sentence summary.
   - `actors`: each kind of user (`kind: person`) and each outside system (`kind: external`).
   - `boxes`: three to seven subsystems (L1). Each needs an id, title and one-sentence summary.
   - `edges`: what passes between actors and boxes, and between boxes. `data` names the thing passed.
3. For each L1 box with real internal structure, write `model/boxes/<l1-id>.yaml` with `parent`, two to seven
   L2 boxes, and the edges between them. An edge may also connect to a box in another file.
4. IDs are lowercase words joined by hyphens, unique across all files.
5. Run `vockpit check`. Fix every ERROR and run it again until it prints OK.
6. Run `vockpit generate`.
7. Write no code and no other files.
8. Tell the user:
   - the boxes you created, level by level;
   - every assumption you made that the brief did not state;
   - every question the brief left open;
   - that they can run `vockpit view` to review the result.
```

## 12. The example: `examples/shop/`

Create these files exactly, then run `vockpit generate` in that folder and commit the output. This is the public demo.

`examples/shop/brief.md`: three or four plain sentences describing an online shop where customers browse a catalogue, place orders, pay through an outside payment provider, and the warehouse is told to ship.

`examples/shop/model/system.yaml`:

```yaml
system:
  id: shop
  title: Online Shop
  summary: Lets customers browse goods, order them and pay online.
actors:
  - { id: customer, title: Customer, kind: person, summary: Browses and buys goods. }
  - { id: payment-provider, title: Payment Provider, kind: external, summary: Takes card payments. }
  - { id: warehouse, title: Warehouse System, kind: external, summary: Picks and ships orders. }
boxes:
  - id: storefront
    title: Storefront
    summary: Shows the catalogue and the cart.
    outputs: [Cart]
  - id: orders
    title: Orders
    summary: Takes orders and tracks them to delivery.
    inputs: [Cart]
    outputs: [Order]
  - id: payments
    title: Payments
    summary: Charges the customer for an order.
    inputs: [Order]
    outputs: [Payment result]
  - id: notifications
    title: Notifications
    summary: Tells customers and the warehouse what happened.
    inputs: [Order event]
edges:
  - { from: customer, to: storefront, data: Browse and add to cart }
  - { from: storefront, to: orders, data: Cart }
  - { from: orders, to: payments, data: Payment request }
  - { from: payments, to: payment-provider, data: Card charge }
  - { from: payments, to: orders, data: Payment result }
  - { from: orders, to: notifications, data: Order event }
  - { from: notifications, to: customer, data: Order confirmation }
  - { from: notifications, to: warehouse, data: Shipping request }
```

`examples/shop/model/boxes/storefront.yaml`:

```yaml
parent: storefront
boxes:
  - { id: catalog-view, title: Catalogue view, summary: Lists goods and shows one item in detail. }
  - { id: cart-view, title: Cart view, summary: Shows the cart and starts checkout. }
  - { id: cart-store, title: Cart store, summary: Keeps each customer's cart between visits. }
edges:
  - { from: catalog-view, to: cart-store, data: Item to add }
  - { from: cart-store, to: cart-view, data: Cart contents }
  - { from: cart-view, to: order-controller, data: Cart }
```

`examples/shop/model/boxes/orders.yaml`:

```yaml
parent: orders
boxes:
  - { id: order-controller, title: Order controller, summary: Receives a checkout request and runs the steps. }
  - { id: create-order, title: Create order, summary: Validates a cart and turns it into an order. }
  - { id: order-repository, title: Order repository, summary: Stores and retrieves orders. }
  - { id: order-status, title: Order status, summary: Moves an order through new, paid and shipped. }
edges:
  - { from: order-controller, to: create-order, data: Order request }
  - { from: create-order, to: order-repository, data: New order }
  - { from: order-controller, to: order-status, data: Payment result }
  - { from: order-status, to: order-repository, data: Status change }
```

Expected result, to be asserted in a test:

- Diagrams: `L0_context`, `L1_system`, `L2_storefront`, `L2_orders`.
- `L0_context` has 4 nodes and 4 edges: `customer -> shop`, `shop -> customer`, `shop -> payment-provider`, `shop -> warehouse`.
- `L1_system` has 4 inner nodes and 3 actor nodes.
- `L2_storefront` has 3 inner nodes and the neighbour `orders`, reached by the edge `cart-view -> orders`.
- `L2_orders` has 4 inner nodes and the neighbour `storefront`, from the edge `storefront -> orders`. Edges declared in `system.yaml` between `orders` and `payments` or `notifications` do not appear, because their `orders` end maps to the focus itself, which is not an inner node.

That last point is a known limit of 0.1: an edge declared at L1 is not shown inside the L2 diagram unless it names an L2 box. Do not work around it. Record it in `CHANGELOG.md` under "Known limits".
